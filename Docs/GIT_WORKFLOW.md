# Разработка нашего форка

Репозиторий: [babkin-kd/SolidWorks-MCP](https://github.com/babkin-kd/SolidWorks-MCP).
Исходный проект: [hjbaard/SolidWorks-MCP](https://github.com/hjbaard/SolidWorks-MCP).
План и критерии готовности: [PLAN.md](../PLAN.md).

## Ветки и стадии

| Ветка | Назначение |
| --- | --- |
| `main` | Проверенные изменения, принятые через PR нашего форка |
| `stage-1-fixes` | Исправления, перенос локальных дополнений, основа API v2 |
| `stage-2-core` | Геометрия, изготовление, конфигурации, сборки и PDM |
| `stage-3-extensions` | Кинематика, печать/сетки и Simulation |
| `archive/local-baseline` | Локальный архив рабочей базы v1; не публикуется автоматически |

Стадии выполняются последовательно. Ветки будущих стадий создаются от принятой предыдущей стадии. Задачи находятся в Issues, стадия задаётся milestone. PR направляется в `main` **нашего форка**. Каждый PR сообщает изменение поведения, способ проверки и ограничения. Приёмка стадии включает native-проверки: успешный CI без SolidWorks недостаточен.

## Локальная рабочая копия

`origin` указывает на наш форк, `upstream` — на исходный проект. Автор коммитов настроен только для этого репозитория. История upstream сохранена. Локальный tag `baseline/sheetmetal.2` и архивная ветка сохраняют предыдущую базу. Незакоммиченные документы v1 сохранены отдельно в игнорируемом `work/local-snapshot/`.

Обновление upstream переносится отдельным изменением после сравнения; не заменять общие исходники старой локальной копией. Для дополнений листового металла сравнивать базовую версию, локальное изменение и новый upstream.

## Проверки и выпуск

Контрольные точки по решению пользователя от 11.10.2026: пакетная отправка после 3–5 законченных связанных блоков либо в конце рабочего дня, после необходимых локальных проверок итогового кандидата. Это правило рабочего процесса, не автоматическое расписание. Детали и отдельный baseline legacy CAD-набора — в [NATIVE_TESTING.md](NATIVE_TESTING.md). Обязательный CI остаётся; cadence не отменяет проверки после штатного merge/push в main.

В пакет включать код и обезличенную сводку: точный проверенный Git SHA, версия/digest/SHA256 wheel, выполненные группы, passed/failed/skipped/not_run/unknown, длительность и ограничения. Сам факт отправки не означает приёмку стадии. При незавершённой приёмке PR остаётся черновиком, main не обновляется до выполнения требований; текущий CAD-вызов ради push не прерывать. Не отправлять полные журналы, рабочие модели и реальные пути. Проверенные результаты привязаны к своему wheel, а не автоматически к каждой следующей версии PR.

Связанные изменения накапливаются в локальных коммитах и проверяются локально, включая установленный wheel/native-сценарии. Для экономии лимитов GitHub Actions отправляем цельный пакет; не делаем push после каждой небольшой правки/обновления документации. Обязательные проверки CI сохраняются и запускаются после общей отправки. Обновление статусов GitHub должно ссылаться на отправленный, доступный там код.

Текущая [контрольная точка dev78](CHECKPOINT_DEV78.md) объединяет пять
measurement/addressing блоков и отдельный legacy-пилот. Точные доказательства,
время и невыполненные gates перечислены в этой обезличенной сводке.

После первой пакетной отправки dev78 CI не создан: GitHub сообщил dirty
при чистом локальном merge-tree. Подробности и ограничения ручного запуска
зафиксированы в сводке; это блокер CI, не разрешение принять PR без проверки.
Доступность workflow_dispatch через текущую интеграцию ещё не подтверждена.

[Локальная контрольная точка dev79](CHECKPOINT_DEV79.md): один законченный
блок после пакета dev78, metadata65/18 и native24/public8 приняты на точном
wheel. Изменения накапливаются локально до следующей пакетной отправки;
блокер CI dev78 этой локальной приёмкой не закрывается.

`Checks` запускается при открытии, обновлении и повторном открытии PR в `main`, а также при push в `main`. Push в рабочую ветку с открытым PR даёт одну PR-проверку; отдельного запуска по push для `stage-*` нет. Для ветки без PR доступен ручной `workflow_dispatch` через GitHub API. Полный набор unit-тестов и сборка wheel/sdist сохраняются; фильтры путей и пропуск обязательной проверки не используются.

Concurrency разделена по workflow, событию и номеру PR либо ref. Новое обновление одного PR отменяет его устаревший незавершённый запуск; проверки других PR, push в `main` и ручные запуски не отменяются этим событием. Отмена устаревшего запуска не засчитывается как успешная проверка: перед принятием нужен результат актуальной версии PR.

На момент прямой API-проверки `main` не защищён: required checks и rulesets отсутствуют. Поэтому обязательность CI пока задаётся правилами проекта и требует проверки актуального результата перед принятием PR; сам workflow не блокирует merge. При настройке защиты следует сохранить имя проверки `unit-and-build`. CI подтверждает unit-тесты и сборку; фактические CAD/PDM/Simulation-операции подтверждаются отдельной native-приёмкой установленного wheel.

- В GitHub Actions сохраняется проверка `unit-and-build`: frozen lockfile, unit-тесты на Windows/Python 3.12, сборка wheel/sdist и metadata-only stdio установленного wheel в отдельном окружении. Только успешный ручной запуск сохраняет candidate artifacts; публикации в PyPI/MCP Registry/GitHub Releases нет. Подробности и локальные доказательства: [FORK_RELEASE.md](FORK_RELEASE.md).
- Native CAD/PDM/Simulation проверяются отдельно в установленной среде. Пропуски и неподтверждённые сценарии указываются явно.
- Установка разработки имеет собственное виртуальное окружение. Рабочая v1 остаётся отдельно. Новый пакет устанавливается в dev-окружение из wheel; затем проверяется stdio и каталог инструментов.
- Реальные CAD-файлы, шаблоны предприятия, локальные настройки, результаты экспорта и секреты не коммитятся. Публичные fixtures допускаются только после обезличивания.
- Не запускать одновременно изменения одной CAD-сессии из v1 и v2 без общего координатора.

## Правила моделей

Новые детали и элементы дерева имеют осмысленные русские названия. Стандартные изделия берутся из согласованных библиотек; повторно используются их файлы и конфигурации. Русское имя экземпляра не изменяет библиотечный файл, артикул и обозначение стандарта. Эти требования входят в критерии проверки функциональных PR.
