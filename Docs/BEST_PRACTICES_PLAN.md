# План регистрации и применения лучших практик SolidWorks

Дата: 11.10.2026. Основание: согласованный подход к использованию официальных
рекомендаций SolidWorks в рабочем процессе ChatGPT → MCP → SolidWorks.

Результат работы — версионируемый реестр инженерных практик, навык выбора и
применения методики, а также подтверждённый сценарий, в котором зависимости
сохраняются в native-модели и работают после изменения размеров и повторного
открытия файла.

План выполняется. Корпус, реестр, карточки и подключённый навык подготовлены;
новые CAD-операции пилота ещё не реализованы. Факты и ограничения проверок:
[BEST_PRACTICES_PROGRESS.md](BEST_PRACTICES_PROGRESS.md). Отметки ниже отражают
выполненные действия и не означают завершения стадий основного плана.

## 1. Место в основном плане

Основной порядок сохраняется: [PLAN.md](../PLAN.md) — исправление → основной
функционал → дополнительный функционал.

- Сбор источников, реестр, описание практик и подготовку навыка можно выполнять
  параллельно завершению стадии 1. Они не добавляют gates к её минимальному
  сценарию простой детали и не требуют вмешательства в текущую CAD-сессию.
- Новые геометрические зависимости и операции пилота относятся к стадии 2,
  прежде всего к пункту 2.1. Их реализация следует формальному переходу к стадии 2.
- Практики сборок изучаются вместе с остальными источниками, но исполняемые
  сценарии сопряжений и внешних ссылок принимаются в собственных блоках пункта 2.6.
- Листовой металл, чертежи и стандартные библиотеки расширяют реестр по порядку
  основного плана. Кинематика и Simulation сохраняют границу стадии 3.

Правила проверок и отправки: [NATIVE_TESTING.md](NATIVE_TESTING.md).
Действующий контракт: [API_V2.md](API_V2.md).

## 2. Разделение ответственности

| Слой | Ответственность | Проверяемый результат |
| --- | --- | --- |
| Реестр | Источники, формулировки, применимость, исключения, версии и доказательства | Для каждой практики понятно, откуда она получена и где подтверждена |
| Навык | Выбор замысла, чтение карточки, уточнение недостающих требований, последовательность действий | Правильная практика выбрана и её точная версия использована |
| Доменная реализация | Повторяемое построение зависимостей и расчёт ожидаемых условий | Зависимость выражена средствами модели в пределах заявленного сценария |
| MCP-фасад | Явные цели, параметры, ревизии, request_id, результаты и журнал | Контракт исполняется без подмены неизвестного исхода успехом |
| Native-проверки | Фактические связи, геометрия, перестроение, сохранение и восстановление | Подтверждена конкретная CAD-операция на точном установленном wheel |

Общие рекомендации остаются рекомендациями с условиями и исключениями.
Обязательные проверки целевого объекта, ревизии, исхода и постусловий выполняет
сервер. Описания навыка и практик не заменяют эти проверки.

## 3. Этапы и результаты

### BP-01. Подготовить корпус источников

- [x] Собрать первый набор из 8–12 доступных первичных материалов и остановить
  расширение после покрытия приоритетных тем: замысел размеров, связи эскиза,
  базы, порядок элементов, сопряжения и внешние зависимости.
- [x] Создать `Docs/BEST_PRACTICES_SOURCES.md`: ID источника, URL, название,
  автор/издатель, продукт, редакция/версия, дата публикации при наличии,
  дата доступа, раздел/страница и состояние доступности.
- [x] Приоритет: справка нужной версии → официальные учебные материалы →
  официальные статьи с инженерными примерами. Рекомендацию автора статьи
  отличать от документированного поведения функции и обязательного ограничения.
- [x] Извлекать утверждения из прочитанного предметного текста. Поисковый
  фрагмент или JS-оболочка страницы не достаточны: найти доступную редакцию либо
  пометить источник как не прочитанный и не основывать на нём карточку.
- [x] Отделять настольный SolidWorks от xDesign и других CAD-продуктов;
  перенос общих принципов отмечать явно и проверять отдельно.
- [ ] Для новых API-вызовов сверять описание с целевой версией SolidWorks
  2023 SP2.1. Документация другой версии не доказывает native-совместимость.

Начальные источники для корпуса:

| Материал | Предмет извлечения |
| --- | --- |
| [Fundamentals of 3D Design and Simulation, 2023](https://www.solidworks.com/sites/default/files/2023-04/Fundamentals3DDesign_SIM_ENG_SV.pdf) | Печатные страницы 10–11: замысел; страница 54: рекомендации по эскизам |
| [SOLIDWORKS Modeling Methodology Part 3](https://blogs.solidworks.com/products/solidworks/solidworks-modeling-methodology-part-3/) | Простота эскиза, размеры и отношения для последующих изменений |
| [Building Stable SOLIDWORKS Assemblies](https://blogs.solidworks.com/products/solidworks/building-stable-solidworks-assemblies/) | Необходимые степени свободы и направленность зависимостей |
| [Simple Machine Part 6, 2016](https://blogs.solidworks.com/tech/2016/06/13056.html) | Частный пример ранних формообразующих скруглений |

Приёмка: каждое извлечённое утверждение имеет точную опору в прочитанном
разделе; ограничения источника сохранены. Полные учебники и чужие изображения
не включаются в реестр: используются собственные формулировки и ссылки.

### BP-02. Определить формат и правила регистрации

- [x] Создать `Docs/BEST_PRACTICES_REGISTRY.md`: порядок регистрации,
  критерии выбора, сила правил, версии и порядок обновления.
- [x] Создать шаблон объяснения `Docs/practices/TEMPLATE.md` и согласованную
  машинную схему метаданных в `engineering/practices/schema.json`.
- [x] Установить обязательные поля: ID, версия, название, ответственный,
  источники и конкретные утверждения, наша интерпретация, применимость,
  исключения, параметры, базы, сохраняемые условия, способ построения,
  требуемые возможности MCP, проверки и ссылки на доказательства.
- [x] Отдельно хранить три оценки: подтверждение источником, принятие
  методики для нашего процесса, проверенность реализации. Утверждённая
  методика может иметь ещё не реализованный исполнитель.
- [x] Для native-доказательств фиксировать сценарий, SolidWorks/SP,
  commit/digest, версию и SHA-256 wheel, дату, исход и ограничения.
- [x] Для результатов использовать passed, failed, skipped, not_run, unknown.
  Для жизненного цикла практики — черновик, проверяется, утверждена,
  заменена, устарела. Исторические результаты не переписывать.
- [x] Существующий ID сохранять при уточнениях; изменение условий применения
  или метода выпускать новой версией. Карточка и её метаданные обновляются вместе.

Приёмка: по карточке можно выбрать методику и составить проверку без
неявных допущений. Источник, вывод автора карточки и собственный тест различимы.
Реестр является единственным источником формулировок; навыки ссылаются на него.

### BP-03. Подготовить первые карточки и матрицу возможностей

- [x] Подготовить 10–15 карточек-кандидатов с приоритетом деталей и эскизов.
- [x] Включить выбор определяющих размеров, симметрию с постоянными отступами,
  симметрию с постоянным шагом, назначение начала координат и баз,
  простоту эскизов, порядок связей/размеров, порядок функциональных и
  косметических элементов, повторное использование параметров.
- [x] Карточки о сопряжениях, необходимых степенях свободы и направленности
  внешних ссылок подготовить как будущие сценарии стадии 2.6.
- [x] Устранить дубли; конфликтующие рекомендации сопоставить по условиям
  применения. Формулировку «всегда» сохранять только для реально обязательного
  ограничения в заявленной области.
- [x] Для каждого правила указать силу: рекомендация, условие выбранного
  сценария либо обязательное техническое ограничение сервера.
- [x] Создать `Docs/BEST_PRACTICES_CAPABILITIES.md`: практика → необходимые
  операции/чтения → фактический публичный контракт → ограничение → стадия плана.
- [x] Различать описание в source, историческую приёмку и проверку текущего
  установленного кандидата. Наличие общего COM-метода не считать публичной
  возможностью MCP.

Начальные ограничения: [SKETCHES.md](SKETCHES.md) описывает запись прямоугольника
с углом в начале модели; [PART_HOLE.md](PART_HOLE.md) — собственные размеры
X/Y/диаметр; [PART_PATTERN.md](PART_PATTERN.md) — ограниченный постоянный шаг.
Создание произвольных symmetric/mirror/equal-связей и уравнений не объявлять
поддержанным на основании чтения связей или исходной совпавшей геометрии.

Приёмка: каждая карточка имеет применимость, исключение, проверяемое условие
и честную оценку исполнимости. Статус «подтверждена источником» не означает
«реализована и принята через MCP».

операции. До этапа BP-06 исполнение новой CAD-цепочки остаётся не подтверждённым.

### BP-05. Реализовать один законченный инженерный пилот стадии 2

Первый исполняемый вариант: «Контрольная пластина» с симметричной парой сквозных
отверстий и постоянными отступами от боковых кромок до центров. Координаты
примеров ниже отсчитываются от левой/нижней базы; выбор native-баз и связей
фиксируется в проекте контракта перед реализацией.

- [x] Описать bounded scope и контракт в `Docs/BEST_PRACTICES_PILOT.md`:
  одна деталь, одна конфигурация, прямоугольное основание, два одинаковых
  сквозных отверстия, явные параметры W/H/T/D/e и согласованное положение по Y.
- [ ] Задать native-зависимость x1=e, x2=W−e и общую высоту центров.
  Выбрать проверяемую реализацию через геометрические связи, зеркальный
  элемент или размерное выражение. Ось должна зависеть от ширины/базы;
  фиксированное x=50 не является осью меняющейся пластины.
- [x] Спроектировать только необходимые создание/чтение зависимостей,
  редактирование ширины и размеров, расширение полного scope ревизии,
  checkpoint и постусловия модели с двумя отверстиями.
- [ ] Проверить совместимость сохранения/повторного открытия с новой структурой.
  Если нужная область lifecycle ещё не поддержана, её ограниченное расширение
  включить в зависимости пилота; существующую приёмку простой базы не переносить.
- [ ] Подготовить доменный алгоритм и MCP-фасад до итоговой сборки wheel.
  Возможность не добавлять в публичный каталог до реализации контракта.
- [ ] Все изменения требуют явных document/configuration/object,
  expected_revision, request_id и native-проверки результата.

Вариант с симметрией и постоянным межосевым шагом описывается в реестре и
проверках выбора навыка. Его CAD-реализация — следующий самостоятельный блок;
первый пилот не расширяется до двух способов построения, сборок, Hole Wizard,
произвольных эскизов, скруглений или нескольких конфигураций.

Приёмка: изменение ширины средствами модели сохраняет выбранное правило без
пересчёта координат со стороны ChatGPT. При запрете нужного параметрического
метода карточка остаётся неисполнимой, а координатная замена не получает её статус.

### BP-06. Принять точный установленный кандидат и навык

- [ ] После промежуточных изменений запускать связанные pure-проверки.
  Перед итоговой сборкой блока — полный pure-набор; повторять его перед новым
  итоговым кандидатом при изменениях исполняемого кода.
- [ ] Собрать чистый итоговый wheel и установить в dev-окружение, сохранив v1.
  Проверять site-packages без исходного PYTHONPATH; записать хеши пакета и навыка.
- [ ] Проверить metadata/stdio, схемы, список инструментов и доставку карточек.
- [ ] Выполнить внутреннюю native-приёмку одним владельцем CAD-сессии.
- [ ] Выполнить публичную MCP-цепочку: параметры/результаты, request_id,
  журнал, версия практики и наблюдаемые постусловия.
- [ ] Проверить применение подключённого навыка к принятой MCP-цепочке.
  Повторное физическое построение выполнять только для отдельного существенного
  свойства; не дублировать подробные negative/recovery-кейсы в двух контурах.
- [ ] Сохранить обезличенную сводку в `Docs/BEST_PRACTICES_PILOT_ACCEPTANCE.md`.
  CAD-файлы и полные журналы оставить в ignored `work/`.

Минимальная матрица пилота:

| Проверка | Ожидаемый результат | Основной контур |
| --- | --- | --- |
| Создание W=100, H=40, T=10, D=6, e=20, Y=20 мм | Два отверстия с центрами X=20/80; фактическая параметрическая зависимость, полный поддержанный BREP и успешное перестроение | Native/MCP пользовательская цепочка |
| Изменение W на 140 мм | Центры X=20/120; e, Y, D и T сохраняются | Та же цепочка |
| Сохранение, закрытие своей модели, повторное открытие | Ссылки заново разрешены; структура и зависимости сохранены | Та же цепочка |
| Изменение W на 120 мм после открытия | Центры X=20/100 без клиентского пересчёта координат | Та же цепочка |
| Изменение D/T и допустимые границы | Ожидаемая форма; отверстия внутри материала и не пересекаются | Domain и targeted native |
| Недопустимые параметры, stale revision | Определённый отказ до записи в рамках контракта | Pure и internal native |
| Повтор request_id | То же задание, без дополнительной записи | Public MCP |
| Known failure и unknown | Подтверждённое scoped restoration либо reconciliation; автоматического повтора нет | Internal native/runtime |
| Неуточнённый замысел, постоянный шаг, неподдержанная операция | Навык корректно уточняет/выбирает другую карточку/сообщает ограничение | Проверки навыка |
| Очистка и соседняя пользовательская модель | Закрыты только свои документы после завершения вызовов; baseline и принадлежащие проверке флаги восстановлены | Native cleanup |

Зависимость подтверждается чтением native-структуры и изменением определяющего
параметра, а не только совпадением исходных координат, объёма или изображения.
Для полного тела использовать существующий проверяемый подход к BREP и
независимым геометрическим фактам; точные допуски закрепить в контракте пилота.

Приёмка: source/domain, installed-wheel, CAD и MCP результаты различимы;
skipped/not_run/unknown не засчитаны как passed. Область accepted относится
только к указанному сценарию, точному wheel и условиям запуска.

### BP-07. Включить принятые практики и расширять по сценариям

- [ ] Принять инженерную применимость карточок ответственным за методику;
  техническую проверенность реализации хранить отдельно.
- [ ] В журнале результата фиксировать ID/версию выбранной практики,
  принятый замысел, допущения и подтверждённые условия; заявлять проверенными
  только реально доступные и выполненные проверки.
- [ ] Решить по опыту пилота, нужна ли доставка реестра через MCP resources
  или поиск. Для первой версии достаточно версионируемых карточек и навыка;
  отдельный сервис реестра и инструмент на каждую рекомендацию не обязательны.
- [ ] Следующие блоки: постоянный межосевой шаг → дополнительные bounded
  сценарии детали → листовой металл/чертежи по PLAN.md → сборочное базирование
  и управляемые внешние ссылки. Каждый блок имеет собственную область приёмки.
- [ ] При изменении практики пересматривать затронутые навыки и проверки.
  Новая версия получает собственную оценку; старые доказательства сохраняются.

Приёмка: навык фактически использует реестр, сервер проверяет выбранные условия,
а пользователь получает модель и объяснение её поведения при редактировании.
Приёмка детали не считается доказательством устойчивости сборок.

## 4. Параллельная работа и контрольные точки

Для BP-01–BP-03 распределить источники по темам: детали/эскизы,
порядок элементов и сборки/внешние ссылки. У каждого исполнителя собственные
источники и файлы; схема, устранение дублей и интеграция принадлежат одному
владельцу. Обзор одного материала несколькими агентами без отдельной причины
не выполнять.

При BP-05 независимые доменные модули, MCP-фасад и pure-проверки готовятся
параллельно по согласованным интерфейсам и отдельным файлам. COM, native-проверки,
установка кандидата и интеграция остаются у одного владельца.

| Контрольная точка | Что должно быть готово |
| --- | --- |
| После BP-01–BP-03 | Корпус, схема, 10–15 карточек и матрица исполнимости |
| После BP-04 | Подключённый навык с проверкой выбора и недоступных возможностей |
| После BP-05–BP-06 | Один законченный инженерный сценарий на точном установленном wheel |
| После BP-07 | Принятая практика в рабочем процессе и следующий самостоятельный блок |

Сроки следующих блоков уточнять по фактическому времени сбора, реализации,
проверок и восстановления первого пилота. Количество карточек не является
оценкой полноты CAD API и не заменяет готовность инженерного сценария.

Обычные изменения внешней документации проверять по содержанию и ссылкам:
они не требуют CAD-приёмки или полного pure-набора. Изменения схем, загрузчика,
упаковки и встроенного guide проверять в затронутой области.

Изменения и локальные коммиты накапливать связанными пакетами. GitHub использовать
через API и Git; отдельный push ради каждой карточки не выполнять. Пакетная
отправка и обязательный CI следуют основному процессу проекта.
