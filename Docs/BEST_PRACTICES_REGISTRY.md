# Регистрация лучших практик SolidWorks

Реестр связывает инженерное правило с первоисточником, областью применения и
проверяемым поведением модели. [План](BEST_PRACTICES_PLAN.md) сохраняет границы
стадий; [карточки](BEST_PRACTICES_INDEX.md) и [источники](BEST_PRACTICES_SOURCES.md)
являются читаемыми представлениями канонического JSON.

## Канонические записи и версии

`engineering/practices/sketches.json`, `features.json` и `assemblies.json`
разделяют владельцев изменений по предметным темам. Формат задаёт
[schema.json](../engineering/practices/schema.json). Описание практики, её
условия и статусы изменяются в JSON; Markdown генерируется из этих записей.
Независимых копий методики в навыке нет.

ID практики постоянен. Изменение применимости, зависимостей или метода требует
новой версии; предыдущие результаты сохраняются в истории Git и приёмочных
манифестах. Результат относится к сочетанию ID/версии/области проверки и
точного окружения. Исправление описки не создаёт новую CAD-приёмку.

## Процесс регистрации

1. Найти первичный материал и прочитать его предметный раздел. Сохранить
   редакцию, продукт, дату доступа, страницу/раздел, дату публикации при наличии.
2. Записать короткое исходное положение. Не превращать частный учебный пример
   в обязательное правило для всех моделей; не переносить xDesign/API другой
   версии на SolidWorks 2023 SP2.1 без проверки.
3. Отдельно сформулировать нашу интерпретацию, применимость, исключения,
   параметры, базы и сохраняемые условия. Предложенные формулы и испытания
   обозначать как наши сценарии.
4. Проверить дубли и конфликты: разные условия могут требовать разных методов.
   Один URL хранить под одним ID источника. При нехватке замысла уточнять
   инженерное требование, а не угадывать его по изображению.
5. Сопоставить требуемые операции с [матрицей возможностей](BEST_PRACTICES_CAPABILITIES.md).
   Описать проверки, назначить ответственного и оставить исход `not_run`,
   пока проверка фактически не выполнена.
6. Выполнить инженерное рассмотрение и затронутые технические проверки.
   Принятие методики и приёмку реализации отмечать раздельно.
7. Подключить точную версию к навыку, проверить её чтение и результат выбора.
   Обновлять карточку при новых наблюдениях; сохранять ограничения доказательств.

## Независимые статусы

| Оценка | Значения | Смысл |
| --- | --- | --- |
| Доступ к источнику | read / partial / unread / unavailable | Прочитан ли предметный текст, а не поисковый фрагмент |
| Подтверждение источником | confirmed / pending | Есть ли точная опора для сформулированного исходного положения |
| Инженерная методика | candidate / accepted / superseded | Принята ли наша интерпретация для её области применения |
| Реализация | not_implemented / partial / source_implemented / wheel_checked / native_accepted | Что подтверждено в техническом контуре |
| Жизненный цикл | draft / reviewing / approved / superseded / deprecated | Состояние сопровождения карточки |
| Исход проверки | passed / failed / skipped / not_run / unknown | Фактический исход конкретного случая |

Подтверждённый официальный принцип может иметь неподтверждённую реализацию.
Утверждение методики также не означает, что сервер уже умеет её исполнять.
Pure-проверка реестра не подтверждает геометрию, установленный wheel или CAD.

## Сила правила и явный замысел

- `recommendation` — предпочтение с применимостью и исключениями.
- `scenario_condition` — сохраняемое условие выбранного инженерного сценария.
- `server_requirement` — обязательная техническая гарантия конкретного
  серверного контракта; этот статус не присваивается общему совету автоматически.

Явное требование пользователя определяет замысел. При противоречии с
рекомендацией объяснить последствия и выбрать соответствующий метод. Обязательные
серверные проверки ревизии, цели и исхода продолжают действовать. Несовместимые
размерные требования требуют уточнения; неизвестный COM-исход не разрешает повтор.

## Роль MCP-сервера

Навык выбирает инженерный замысел и объясняет метод. Сервер публикует фактический
каталог возможностей, разрешает явные объекты и выполняет реализованный метод
в своей ограниченной области. Для параметрического сценария сервер должен
создать и прочитать native-зависимости, включить их в ревизию и подтвердить
постусловия изменения. При передаче ID/версии практики одного этого ярлыка
недостаточно: сервер проверяет параметры и реальные условия своего контракта.

Общие советы о порядке элементов не обязаны становиться отдельными tools.
Практика становится серверным контрактом, когда появляется конкретный
инженерный сценарий с воспроизводимыми входами, зависимостями и проверками.
Технические гарантии цели, ревизии, request_id, исхода и восстановления
сохраняются независимо от того, прочитан ли навык клиентом.

Доставка реестра через MCP resources/поиск остаётся возможным следующим решением
после пилота. Публикация ресурса сама по себе не обеспечивает чтение клиентом,
актуальность его снимка или выполнение native-проверок.

## Доказательства и работа с Git

Для native/MCP-проверок нужны версия пакета, SHA-256 wheel, Git SHA/source digest,
область проверки и результат; для native также SolidWorks/SP. Журналы и модели
остаются в ignored `work/`, в Git попадают обезличенные сводки и ссылки на
локальные свидетельства. Чужие модели и изменения не используются как фикстуры.

Проверить реестр и актуальность Markdown:

```powershell
./.venv/Scripts/python.exe -X utf8 scripts/verify_best_practices.py
```

После правки канонических записей обновить представления:

```powershell
./.venv/Scripts/python.exe -X utf8 scripts/verify_best_practices.py --write-docs
```

Верификатор проверяет схему, ссылки между записями, дубли и согласованность
статусов. Он не заменяет чтение источника или независимую CAD-приёмку.
После обновления реестра генерировать снимок навыка командой
`scripts/build_best_practices_skill.py --write --deploy --check-deployed`.
Подключённый каталог .agents/skills и исходный skills/ не редактировать
независимо: проверяемый генератор сохраняет единственный канонический текст.
Фактическое обнаружение и ограничения оценки описаны в
[проверке навыка](BEST_PRACTICES_SKILL_ACCEPTANCE.md).
Связанные изменения фиксируются локально одним блоком; пакетная отправка и CI
следуют [NATIVE_TESTING.md](NATIVE_TESTING.md).
