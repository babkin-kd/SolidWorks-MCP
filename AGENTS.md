# Работа над SolidWorks MCP

- Выполнять согласованный `PLAN.md` по стадиям: исправление, основной функционал, дополнительный функционал. Не считать стадию завершённой по одному успешному CI: native-приёмка обязательна.
- GitHub использовать **напрямую через подключённые API и Git**. Для работы с GitHub браузер не использовать — это явно выбранный пользователем способ работы.
- `origin` — наш форк `babkin-kd/SolidWorks-MCP`, `upstream` — `hjbaard/SolidWorks-MCP`. PR направлять в наш форк. `main` сохранять стабильным; текущая работа первой стадии находится в `stage-1-fixes`.
- Сохранять отдельную рабочую установку v1 и локальные правки пользователя. Новые wheel устанавливать в dev-окружение проекта; проверять установленный пакет без `PYTHONPATH` исходников.
- В каталог API v2 включать только реализованные инструменты; без legacy-алиасов и без объявления неподтверждённых CAD/PDM/Simulation-возможностей. Контракт кандидата описан в `Docs/API_V2.md`.
- Для изменений модели нужны явный документ/конфигурация/объект, ревизия, request_id и проверка постусловий. Тайм-аут ожидания не означает отмену COM. Неопределённый исход требует согласования состояния; его нельзя объявлять успехом или автоматически повторять.
- Новые детали, компоненты и элементы дерева называть по-русски. Стандартные элементы максимально брать из утверждённых библиотек, повторно использовать их файлы/конфигурации; не менять библиотечные имена файлов, артикулы и обозначения стандартов ради локализации.
- Реальные CAD-файлы, шаблоны предприятия, локальные PDM-данные и журналы заданий оставлять вне публичного Git. Сохранять лицензию и атрибуцию upstream.
- Пропущенные native-тесты не засчитывать как пройденные. В отчёте различать проверку искусственного доменного сценария, установленного wheel и фактической CAD-операции.
